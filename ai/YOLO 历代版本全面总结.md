# YOLO 历代版本全面总结（2016–2026）

# 0. 导读

## 0.1 本文怎么读：三层追问

同一段技术史，可以用三种问法去读，得到的收获完全不同：

- 它解决的是**表示问题、优化问题，还是工程问题**？——这决定了它的创新落在哪一层。
- 我若要在自己的项目里复现它，**最短路径是什么、最常踩的坑是什么**？——这决定了它能不能落地。
- 它的**成本模型**（算力、内存、延迟、维护）在什么业务下才划算？——这决定了要不要换版本。

全文由四块构成：

- **第 1 节**：十年大图景与谱系；
- **第 2 节**：统一的评价尺子（指标口径、效率度量、消融归因、后处理）；
- **第 3 节**：**历代版本详解**——14 个版本（YOLOv1 → YOLO27）合并到同一目录下，每个版本一节，动机、原理、公式、消融、争议、遗产、Demo 收在同一节内；
- **第 4–5 节与附录**：横向主线、开放问题。

## 0.2 贯穿全文的示例主线

为避免讨论停在抽象指标上，全文反复回指同一个场景：

```
COCO 对比线：   固定 val2017、固定 imgsz、固定 batch → 只比 mAP50-95 / params / FLOPs / T4-latency
部署产出线：    训练权重 → ONNX → TensorRT / OpenVINO → 边缘盒子的 FPS 与功耗
业务验收线：    质检漏检率 / 误检率 → 它和 mAP 的相关性到底成不成立？
```

三条线并置的意义在于祛魅：**“COCO 涨 1 个点”和“产线少漏一个缺陷”之间没有必然等价**。一个只在大目标上提升的版本，可能在产线的微小缺陷场景里毫无收益。

# 1. 大图景：十年演进的时间轴与谱系

## 1.1 一个范式如何改写目标检测

2016 年之前，目标检测的主流答案是“两步走”：先用选择性搜索或区域提议网络（RPN）在一张图上生成约 2000 个候选区域，再让分类器逐个判断“这是什么”。这套流程的精度在当年无可挑剔，但它有一个无法回避的结构性代价——**每条候选区域都要独立地过一遍网络**。R-CNN 在 GPU 上跑一张图需要数十秒；Faster R-CNN 虽已大幅优化，仍难以稳定突破实时（>30 FPS）这条线。

YOLO（You Only Look Once）的出现，不是“把某一步做得更快”，而是**取消了那一步**：它把“找区域”和“分类”合并成一次前向传播的回归问题。输入一张图，输出一组框和类别，中间没有候选区域、没有 RoI 池化、没有逐框并行分类。

这个转变带来的第一层价值是速度，但更深远的影响是**重新定义了问题的形态**：检测从此可以被当作一个端到端可训练、可微分的任务来讨论。此后十年 YOLO 的每一次演进，本质上都是在这个“单阶段骨架”上，逐个补齐它相比两阶段方法所欠缺的能力。

而如果不加滤镜地看这十年，会发现一个规律：**瓶颈在不断转移**。

| 时间        | 瓶颈          | 主要应对                                       |
| --------- | ----------- | ------------------------------------------ |
| 2016–2018 | 定位精度与多尺度表示  | v1 定位差 → v2 锚框 + BN → v3 三尺度 + 特征融合        |
| 2020–2022 | 训练效率与工程可用性  | v4 消融归因 → v5 工具链 → v6 部署导向 → v7 训练期技巧      |
| 2023–2024 | 标签分配与推理链路   | v8 动态分配 → v9 梯度信息 → v10 取消 NMS → v11 轻量注意力 |
| 2025–2026 | 端到端可部署与任务覆盖 | v12 注意力中心 → v26 边缘优先 → v27 多任务 + 开放词汇      |

## 1.2 四阶段时间轴

下面的阶段划分不按年份均分，而按**主导矛盾的转移**：当一类问题被基本解决，它就不再是论文竞争的焦点，注意力会自动迁移到下一个瓶颈上。因此表中除了“谁在什么时候做了什么”，还专门列出了每个版本试图回答的那个问题。

| 版本            | 年份   | 发布方         | 关键机制                             | 关键问题            | COCO AP（参考）         | 速度（参考）          |
| ------------- | ---- | ----------- | -------------------------------- | --------------- | ------------------- | --------------- |
| v1            | 2016 | Redmon（UW）  | 单阶段回归、7×7 网格                     | 检测能否一步回归？       | 63.4 VOC07 mAP      | 45 FPS（Titan X） |
| v2 / YOLO9000 | 2017 | Redmon      | 锚框 + K-means、Darknet-19          | 如何兼顾速度与召回？      | ~44（COCO，544）       | 40–67 FPS       |
| v3            | 2018 | Redmon      | 三尺度、Darknet-53、独立 logistic       | 小物体与多尺度如何解？     | 33.0 AP / 57.9 AP50 | 51 ms           |
| v4            | 2020 | Bochkovskiy | CSPDarknet53 + SPP + PANet + BoF | 哪个 Trick 真正有效？  | 43.5 AP             | ~65 FPS（V100）   |
| v5            | 2020 | Ultralytics | Focus / CSP / PANet / 自动锚框       | 工程可用性是否也是贡献？    | 50.7 AP50（v5x）      | 视型号             |
| v6            | 2022 | 美团          | EfficientRep / Rep-PAN / TAL     | 工业吞吐优先怎么设计？     | 52.5 AP50（v6-s）     | T4 量化           |
| v7            | 2022 | Wang(CY)    | E-ELAN / 辅助头 / 计划重参数化            | 训练期技巧可“零推理成本”吗？ | 56.8 AP（E6）         | 30+ FPS         |
| v8            | 2023 | Ultralytics | C2f / Anchor-free / TAL + DFL    | 分配策略是否比结构更重要？   | 53.9 AP（v8x）        | 视型号             |
| v9            | 2024 | Wang(CY)    | PGI + GELAN                      | 信息瓶颈如何量化与缓解？    | 55.6 AP（v9e）        | —               |
| v10           | 2024 | 清华          | 一致双分配、NMS-free                   | 无 NMS 的代价是多少？   | 54.4 AP（v10x）       | 端到端             |
| v11           | 2024 | Ultralytics | C3k2 + C2PSA                     | 注意力“轻量嵌入”的边界在哪？ | 54.7 AP（11x）        | —               |
| v12           | 2025 | Tian 等      | A² 区域注意力 + R-ELAN                | 注意力能否成为实时骨干主体？  | ~55+ AP             | 待核              |
| v26           | 2026 | Ultralytics | 原生端到端、CPU 优化                     | 边缘 CPU 实时是否可达？  | 官方口径                | +43% CPU（口径待核）  |
| v27           | 2026 | Ultralytics | 28 模型 × 7 任务、YOLOE-27            | 开放词汇能否进入实时栈？    | 官方口径                | 待核              |

上表的数字只有在**口径统一**时才具有可比性。所谓口径，至少包含六项：

① 评测数据集与 val 划分（COCO val2017 还是 test-dev）；

② 输入分辨率 imgsz（640 与 1280 之间的差距，可能大于两个版本之间的差距）；

③ 硬件型号（Titan X / V100 / T4 / Xeon / Jetson 完全不是一回事）；

④ 数值精度（FP32 / FP16 / INT8）；

⑤ 是否包含 NMS 等后处理；

⑥ 是否使用 TTA 或多尺度测试。

更关键的是**主指标是 AP50 还是 AP50-95**——AP50 对定位质量不敏感，AP50-95 才是 COCO 的主指标，同一个模型在这两个指标上的“代际差距”可能完全不同。

上表混用了两种口径（部分行标 AP、部分行标 AP50），跨行比较前务必先对齐。

关于表中的数字，还有三点需要提前说明：

- **v1–v3 的数字不能与 v4 之后直接比。** 前三代主要报告 PASCAL VOC 2007 的 mAP（VOC 只有 20 类，指标定义也不同），从 v4 开始才统一到 COCO。表中 v1 一行的 `63.4` 是 VOC mAP，不是 COCO AP。
- **“速度”列的含义随时代变化。** v1–v4 报告的是 Darknet 框架下的 FPS 或单帧毫秒，v6 之后更多报告 TensorRT 量化后的延迟。FPS 与延迟不是同一个量（存在批处理与流水线效应），不能互相换算后比较。
- **v26 / v27 全部标记为“官方口径 / 待核”。** 这两代的最新数字来自厂商发布材料，尚无充分的第三方独立复现。正式引用前必须找到官方文档与至少一份第三方基准，并写明测量条件；否则一律标注为“待核实”，不得写进结论表。

## 1.3 技术谱系树

要理解“为什么同时存在这么多 YOLO”，必须先区分两种关系：**代码谱系（fork）**指某版本直接基于上一版本的代码库继续开发，实现细节、训练流程、配置格式高度一致；**思想谱系（influence）**指某版本并未复用代码，但采用了前者的某个机制，或对前者的缺陷作出回应。

整个 YOLO 生态的特点是：**代码谱系在 v3 之后基本断裂，思想谱系则一直延续。** Redmon 退出后，v4 / v5 / v6 / v7 / v8 之间几乎不存在代码级的父子关系，但它们几乎都在回答同一个问题——“怎样比前一版更快更准”。因此对比版本时，应当比较**机制**，而不是比较**血统**。

```
两阶段范式（R-CNN → Fast / Faster R-CNN）
        │  思想影响：锚框先验(v2)、候选框与分类分离的思路
        ▼
┌─ Darknet 线 ────────────────────────────────────────────────┐
│  Redmon:  v1 ──▶ v2 / YOLO9000 ──▶ v3                      │
│           (代码同源，架构连续演进)                            │
└─────────────────────────────────────────────────────────────┘
        │  思想延续
        ▼
┌─ Darknet 社区的延续 ────────────────────────────────────────┐
│  v4 (AlexeyAB) ──▶ v7 (WongKinYiu) ──▶ v9 (PGI / GELAN)    │
│           BoF / BoS 归因 → 训练期技巧 → 梯度信息可编程         │
└─────────────────────────────────────────────────────────────┘

┌─ Ultralytics 线（统一平台）─────────────────────────────────┐
│  v5 ──▶ v8 ──▶ v11 ──▶ v26 ──▶ v27                          │
│  工具链 → 动态分配 → 轻量注意力 → 端到端边缘 → 多任务 + 开放词汇 │

┌─ 独立分支 ──────────────────────────────────────────────────┐
│  美团:      v6 ──▶ v6.1 / 6.2 / 6.3  （TAL、SIoU、量化、工业）│
```

## 1.4 命名混乱与“版本号 ≠ 架构代际”

如果说 1.3 讲的是“技术上是四条线”，那么这一节讲的是“命名上它们却被塞进了一个数字序列”。这件事造成的实际困扰，比它看起来更严重。

**命名史的关键节点：**

- **2018 年之后**：Redmon 于 2020 年宣布退出计算机视觉研究，v3 之后的官方序列事实上终止。
- **v4（2020）**：由 Alexey Bochkovskiy 发布。它并非官方续作，而是在获得社区认可后沿用了 v4 这个名字；其价值在于用一次大规模、可复现的消融实验，把当时散落各处的训练技巧系统化。
- **v5（2020）**：Ultralytics 直接使用 v5 命名。由于没有配套论文，当时引发了“一个没有论文的工程实现，是否有资格占用一个版本号”的争论。
- **v6（2022）**：美团视觉团队发布，走的是与 Ultralytics 完全独立的技术路线（重参数化 + 部署导向）。
- **v7（2022）/ v9（2024）**：由原 v4 团队发布，延续 Darknet 社区的技术脉络。
- **v8 / v11 / v26 / v27**：Ultralytics 产品线。注意它**跳过了 v9、v10 的编号**（这两个号已被其它团队占用），并在 v11 之后转向年份式命名（YOLO26、YOLO27），这本身就说明“数字版本号”这套体系已经用不下去。
- **v10（2024）/ v12（2025）**：分别来自清华团队与独立学术团队，与 Ultralytics 产品线无代码关系。

**由此可以得出一条判断标准：不要看编号，看机制。** 具体可用三把尺子：

| 尺子        | 含义                  | 典型例子                                     |
| --------- | ------------------- | ---------------------------------------- |
| 机制是否不可替代  | 该版本提出的东西，能不能被简单替换掉？ | v10 的一致双分配（移除 NMS 是范式级变化）；v3 的三尺度预测      |
| 是否改变了社区实践 | 它是否成为后来者的默认做法？      | v5 的自动锚框与导出链；v4 的 Mosaic 与 CIoU；v8 的 TAL |
| 是否可公开复现   | 有没有论文 + 代码 + 权重三件套？ | v5 / v8 无论文但代码权重齐全；v26 / v27 细节依赖官方文档    |

按这三把尺子重新审视，会得到几个与“数字顺序”直觉相反的结论：

1. **v5 的价值主要在工程与生态**（自动锚框、`hyp.yaml` 超参可复现、完整导出矩阵）。它的学术新颖性弱，却是过去五年被实际使用最多的实现之一。“工程贡献算不算研究贡献”这个问题，v5 给出了实践层面的答案。
2. **v4 与 v7 的价值在方法论。** 它们并未发明全新模块，而是把“哪些技巧真正有效、代价是多少”做成了可核查的消融表；这类工作的意义是**降低整个领域的试错成本**。
3. **v10 是少见的范式级节点。** 在此之前的版本都在优化“如何更好地产生候选框并去重”，v10 直接把去重环节从推理链路中拿掉了。
4. **版本号靠后的不一定更先进。** v6 与 v8 是同期产物，目标函数不同（工业吞吐 vs 通用体验），不存在“v8 是 v6 的升级”。

因此每节展开时都会先给出一条“命名词条”，明确它在谱系中的真实位置。例如：

> **命名词条**：`Ultralytics YOLOv8 ≠ 原 YOLO 谱系的续作，而是“统一平台线”的起点；它与同期的 v9、v10 是并列关系，而非继承关系。`

## 1.5 小结：一条主线与三组张力

把 1.1–1.4 压缩成一句话：**YOLO 的十年，是在“速度与部署成本”的硬约束下，不断转移瓶颈、逐个补齐能力的十年。**

在这条主线之下，有三组始终没有被彻底解决的张力，它们会在后面每一节里反复出现，也是判断一个版本“是不是真进步”的关键：

- **精度 ↔ 速度**：几乎每一次涨点都伴随某种代价，差别只在于代价被放在推理期（如 BoS），还是训练期（如 BoF）。
- **结构创新 ↔ 训练技巧**：从 v4 起，涨点越来越多来自损失、分配与增强，而不是网络结构本身。判断一个版本时，必须问清楚“这个收益能不能脱离训练流程单独存在”。
- **通用性 ↔ 专用性**：COCO 上的通用最优，与工业产线、边缘设备上的专用最优，往往是两套不同的取舍（v6 与 v26 是这一张力的直接产物）。

## 1.6 三条读者路径

| 目标   | 路径                                      | 每个节点的必做实验                                     |
| ---- | --------------------------------------- | --------------------------------------------- |
| 理解原理 | v1 → v3 → v8 → v12                      | 手写一遍 v1 损失；复现 v3 的三尺度输出形状；可视化一次 v8 的 TAL 分配结果 |

# 2. 评价与方法论工具箱

讨论“哪个版本更好”之前，必须先立一把尺子。这一节把后面反复用到的指标、度量、归因方法与后处理一次讲清。

## 2.1 精度指标

- **P / R / F1**：`P = TP/(TP+FP)`、`R = TP/(TP+FN)`、`F1 = 2PR/(P+R)`。
- **AP 的定义链**：按置信度排序 → 逐点计算 P 与 R → 求 P-R 曲线下面积（COCO 用 101 点插值）→ **IoU 阈值取 0.5 时的 AP 记为 AP50**。
- **mAP50-95**：IoU 从 0.5 到 0.95、步长 0.05 共 10 个阈值下的 AP 取平均。**这是 COCO 的主指标**，也最常被含糊地称作“mAP”。
- **分尺度 AP**：按真实框面积划分 `AP_small (<32²)`、`AP_medium (32²–96²)`、`AP_large (>96²)`。报小物体性能必须看 AP_small，否则涨点可能完全来自大物体。

**最容易犯的两个错**：

1. 把 AP50 当作唯一指标。AP50 对定位漂移极不敏感，一个“框得很大很糊但类别对”的预测也能拿到高分；**AP75 才是定位质量的敏感指标**。跨版本比较应同时给 AP50 与 AP50-95。
2. 拿不同 val 划分的 AP 直接比。COCO val2017 与 test-dev 之间、以及不同评测脚本版本之间都存在系统性偏差。

## 2.2 效率指标

四个常用量：**params（参数量）**、**FLOPs / MACs（乘加数）**、**latency（单帧时延）**、**FPS（吞吐）**。

- **FPS ≠ 1 / latency。** 批处理、流水线、GPU 并行会让吞吐远高于单帧时延的倒数。**边缘场景必须报 latency（尤其是 P99 尾延迟）**，云端场景可以报吞吐。
- **FLOPs 不是延迟的代理。** 同样的 FLOPs，在不同硬件、不同算子支持度下，延迟可能差数倍。注意力这类操作在 GPU 上高效，在部分 NPU 上却可能退化成低效算子。
- **报数时至少标注六项**：硬件型号、数值精度、是否含前后处理、batch size、imgsz、是否含 NMS。

> **图 2-1（待补）**：同一个模型在 `T4-FP16`、`Jetson Orin-INT8`、`Xeon-ONNX-FP32` 三种配置下的延迟条形图，用于说明“FLOPs 相同、延迟差数倍”。

## 2.3 训练成本与可复现性

除了精度与速度，还要记录：训练用了多少卡、多少 epoch、总 GPU-hours；以及**是否公开了训练脚本与权重**——这是可复现性最硬的证据。

复现结果与论文不一致时，差异通常来自这几处：数据划分方式、增强的随机性、预训练权重来源、超参搜索预算、评测脚本版本、NMS 实现差异、letterbox 填充方式。定位问题时应逐项排除，而不是先怀疑结构。

## 2.4 训练三件套的演进地图

把损失、标签分配、数据增强三件事拉成时间线，能看到一个清晰的重心迁移：

- **损失**：MSE（v1）→ BCE + CIoU（v4 / v5）→ DFL + CIoU（v8）→ 去 DFL（v26，待核）。
- **标签分配**：单格负责（v1）→ IoU 阈值 / 最优锚框（v2–v5）→ SimOTA（v6 中期）→ TAL（v6.1 / v8）→ 一致双分配（v10）。
- **数据增强**：随机缩放与翻转（v2–v4）→ Mosaic（v4 起）→ MixUp / Copy-Paste → 自监督与伪标签。

> **图 2-2（待补）**：以损失、分配、增强为三条纵轴、年份为横轴，把各版本点上去。图中应能直接看出：**v8 之后的创新主要落在“分配与损失”，而不是骨干结构。**

## 2.5 结构解耦：统一的描述语言

任何一代 YOLO 都可以写成同一个四元组：

```
Backbone（特征提取） → Neck（多尺度融合） → Head（预测） → Post（后处理）
                                  ＋
              Training-Only 组件（辅助头、可逆分支、重参数化分支）
```

用这个框架去读每一个版本，先问一句：**这次的创新落在哪个槽位？它是结构创新，还是训练技巧？两者能否拆开单独验证？** 这一问能过滤掉大量“看起来很深、实际只是加了个训练技巧”的说法。

> **图 2-3（待补）**：以 v4 为例，在同一张网络图上用两种颜色分别标出“推理时存在的模块”与“仅训练时存在的模块”，这就是 BoF/BoS 的可视化定义。

## 2.6 消融方法论与归因陷阱

消融实验（ablation）是判断“涨点来自哪里”的唯一手段，但有几个高频陷阱：

1. **超参不匹配**：给新组件配了调优过的超参，基线却用默认值——涨点可能来自调参而非组件本身。
2. **增强与训练时长的耦合**：更强的增强通常需要更长的训练，涨点可能来自 epoch 变多。
3. **后处理混入对比**：单阶段与两阶段（或端到端模型）对比时，是否双方都关掉了 NMS。
4. **口径漂移**：imgsz 从 640 提到 1280 本身就会涨点，若只在实验组改动，结论无效。

规范的消融报告应当是一张**从基线逐项累加**的表，且每次只改一个变量。

## 2.7 推理后处理与端到端

**NMS 家族**：Greedy NMS → Soft-NMS → DIoU-NMS（v5 / v6）→ 无 NMS（v10 / v26）。

NMS 有三个代价：① 不可导，阻断端到端训练；② 需要排序与串行比较，延迟随候选框数量波动；③ 依赖 IoU 阈值这一超参，密集场景下容易误删正确框。

> **图 2-4（待补）**：同一张人群密集图，分别展示 `NMS IoU=0.5` 与 `0.7` 时的“漏框”与“重框”，再展示 v10 一对一分支的输出天然无重叠。

## 3.1 YOLOv1（2016）：单阶段检测的诞生

> **命名词条**：Darknet 线起点；YOLO 一切版本的共同祖先。

### 3.1.1 背景与动机

2016 年前后，目标检测被两阶段方法（R-CNN 系列）主导：先生成约 2000 个候选区域，再逐个分类。流程冗长、推理缓慢，难以实时。YOLOv1 的目标是把检测重构为一个**单一回归问题**，一次前向同时给出位置与类别。

### 3.1.2 论文与仓库

| 项目        | 内容                                                                                     |
| --------- | -------------------------------------------------------------------------------------- |
| 论文        | *You Only Look Once: Unified, Real-Time Object Detection*，CVPR 2016，arXiv:1506.02640 ✅ |
| 官方实现      | `pjreddie/darknet`（C 语言），模型配置 **`cfg/yolo.cfg`**，权重 **`yolo.weights`**（VOC 20 类）✅      |
| 版本专属标识    | 输入 448×448、网格 7×7、无锚框、每格 2 框共享类别                                                       |
| 独立客户端（社区） | **`abeardear/pytorch-YOLO-v1`** ✅（已核实存在，约 679 star，是目前最常用的 PyTorch 复现之一）               |
| 常见误区      | **没有官方 PyTorch 版**（官方只有 C 语言 Darknet）；社区复现众多，须核对权重来源 ⚠️                                |

> **关于「三个版本共用同一个仓库」**：这是事实而非笔误——Redmon 在 2016–2018 年间用同一套 Darknet 代码发布 v1 / v2 / v3，三代**共用仓库、共用可执行文件**，区别只在 **模型配置文件与权重文件**（`cfg/yolo.cfg` → `cfg/yolov2.cfg` → `cfg/yolov3.cfg`）。若要区分，请看配置文件与权重名，而不是仓库地址。

### 3.1.3 核心原理

**小白版**：把 448×448 的图切成 7×7 的网格，每个格子有一位“管家”，负责报告中心落在本格内的物体——有没有、是什么、框多大。

**算法级**：

- 输出张量为 `7×7×(B×5 + C)`，取 `B=2, C=20`（PASCAL VOC）时为 `7×7×30`。
- 每个格子的 2 个边界框**共享同一组类别概率**——这是后来密集小物体失效的根因。
- 置信度的定义合成了“有无物体”与“框得准不准”：`Pr(Object) × IoU(pred, truth)`。
- 推理时用 NMS 去除重叠框（注意：NMS 从第一代起就是链路的一部分，直到 v10 才被移除）。

### 3.1.4 关键公式与损失

总损失是分段的**和方差损失**，三部分各有权重：

- **定位项**（仅对含物体的框计算）：
  `λ_coord · Σ [ (x-x̂)² + (y-ŷ)² + (√w-√ŵ)² + (√h-√ĥ)² ]`，其中 `λ_coord = 5`。
- **置信度项**：含物体框权重 1，无物体框权重 `λ_noobj = 0.5`（用于压制大量背景格产生的梯度）。
- **分类项**：对含物体的格子计算 20 维类别平方误差。

**为什么宽高开根号？** 同样的绝对误差，落在小框上造成的 IoU 损失远大于大框。对 `w`、`h` 取平方根后再算误差，相当于给大框降权、给小框加权，使定位项对大框不敏感、对小框敏感。

> **图 3-1（待补）**：画 7×7 网格 → 标出物体中心格 → 展开该格的 `2×5` 个框参数与 20 个类别值 → 手算一次定位项与无物体置信度项。

### 3.1.5 消融与关键数字

- VOC 2007：**63.4 mAP @ 45 FPS**（Titan X）；轻量版 Fast YOLO 为 52.7 mAP @ 155 FPS。
- 论文的误差分析显示：YOLO 的速度远超两阶段方法，但**定位误差显著更高**（论文自身亦承认）。

### 3.1.6 争议与批判

- **缺陷是结构性的，不是调参能救的。** 每格只预测一组类别、两框共享类别，决定了它在鸟群、人群这类密集小目标上必然失效。
- **直接回归绝对坐标**，导致对训练集中未出现过的宽高比泛化差。
- 论文把误差分为定位 / 背景误检 / 类别三类，明确指出主要短板在**定位**——这为 v2、v3 指明了方向。

### 3.1.7 局限与遗产

- **遗产**：单阶段 + 端到端范式；“正负样本加权”的损失设计思想；用 IoU 定义置信度的做法。
- **淘汰**：网格内一类一预测、直接回归绝对坐标、用平方误差做定位。

### 3.1.8 Demo 与落地

原始 Darknet 环境配置较繁琐，入门建议用社区 PyTorch 复现：

**路线 A：官方 Darknet（C）**

```bash
git clone https://github.com/pjreddie/darknet
cd darknet && make
# v1 权重：yolo.weights（PASCAL VOC 20 类），下载入口见官方页面 pjreddie.com/darknet/
./darknet detect cfg/yolo.cfg yolo.weights data/dog.jpg
```

**路线 B：社区 PyTorch 复现**（仓库已核实存在 ✅）

```bash
git clone https://github.com/abeardear/pytorch-YOLO-v1
cd pytorch-YOLO-v1
pip install torch torchvision opencv-python numpy
python detect.py --image test.jpg
```

### 3.1.9 延伸与开放问题

同期 SSD 与后来的 RetinaNet 走了不同的单阶段路线。理解“单阶段为何长期打不过两阶段”，需要引入正负样本极度失衡的视角——这正是 Focal Loss 的出发点。

## 3.2 YOLOv2 / YOLO9000（2017）：更快更强

> **命名词条**：Darknet 线；从“纯回归”回摆到“先验框”，是范式上最值得玩味的一次转折。

### 3.2.1 背景与动机

v1 速度快但精度不足、召回率低。v2 的问题意识很明确：**如何在不牺牲速度的前提下，系统性地补齐精度？**

### 3.2.2 论文与仓库

| 项目        | 内容                                                                                                                                          |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 论文        | *YOLO9000: Better, Faster, Stronger*，CVPR 2017，arXiv:1612.08242 ✅                                                                           |
| 官方实现      | `pjreddie/darknet`，模型配置 **`cfg/yolov2.cfg`**（COCO 80 类）、**`cfg/yolo-voc.cfg`**（VOC 20 类），权重 **`yolov2.weights`**、**`yolov2-voc.weights`** ✅ |
| 版本专属标识    | 首次引入锚框 + K-means（5 个先验）、Darknet-19 骨干、支持 320–608 多尺度输入                                                                                      |
| 独立客户端（社区） | **`longcw/yolo2-pytorch`** ✅（已核实存在，约 1560 star，YOLOv2 最主流的 PyTorch 复现）                                                                      |
| 千类版本      | YOLO9000 的 9000 类权重为 `yolo9000.weights`，依赖 WordTree 联合训练 ⚠️（获取途径以官方页面为准）                                                                    |

### 3.2.3 核心原理

**Better（精度）**

- **Batch Normalization**：每个卷积层后加 BN 并移除 Dropout，mAP 提升约 2%。
- **高分辨率分类器**：先以 448×448 微调分类网络，再迁移到检测。
- **锚框 + K-means**：借鉴 Faster R-CNN，用聚类从数据集中学习先验框尺寸，替代 v1 的直接回归坐标。
- **直接位置预测**：限制中心点偏移落在本格内，训练更稳定。
- **passthrough 细粒度特征**：把 26×26 的特征图拼接到 13×13，补回小物体的空间细节。

**Faster（速度）**：换成 19 层的 Darknet-19 骨干，精度接近 VGG16 而计算量更小。

**Stronger（类别覆盖）**：用 WordTree 把 COCO 与 ImageNet 的类别层次化联合，使模型能检测超过 9000 类。

### 3.2.4 关键公式与损失

- **K-means 的距离改用重合度**：`d(box, centroid) = 1 - IoU(box, centroid)`。因为框的尺寸差异极大，欧氏距离会被大框主导，用 IoU 才反映“形状接近程度”。
- **位置回归**：`b_x = σ(t_x) + c_x`、`b_y = σ(t_y) + c_y`，把预测中心限制在所属格内；尺寸 `b_w = p_w·e^{t_w}`、`b_h = p_h·e^{t_h}`，把宽高表示为先验框的指数倍数。

> **图 3-2（待补）**：在 5 个聚类质心的先验框上，演示 `σ` 如何把中心锁在格内、指数如何把宽高缩放到先验的倍数。

### 3.2.5 消融与关键数字

- VOC 2007：**78.6 mAP @ 40 FPS**；COCO 约 44 AP（544 输入）。
- 论文的消融表给出的贡献排序大致为：BN > 高分辨率分类器 > 锚框 > 多尺度训练。

### 3.2.6 争议与批判

- **锚框的引入是一次范式回摆**：v1 反对两阶段的先验设计，v2 又把锚框借回来。这说明**纯回归的收敛性不足以支撑高精度**，先验框在当时仍是必要的优化脚手架。
- **K-means 先验依赖数据集分布**：换数据集需要重新聚类，跨域时先验可能完全不匹配。

### 3.2.7 局限与遗产

- **遗产**：BN、锚框、多尺度训练（每 10 个 batch 随机换输入尺寸）、sigmoid 位置约束，都成为后续默认配置；WordTree 的层次化类别思想，在今天演化为开放词汇检测。
- **遗留**：锚框尺寸的超参敏感性、类别不均衡问题。

## 3.3 YOLOv3（2018）：多尺度预测的经典

> **命名词条**：Darknet 线收官之作；此后 v4–v9 的骨架几乎都建立在它之上。

### 3.3.1 背景与动机

v2 在小物体上依然不佳，且与当时的最优方法（如 RetinaNet）存在明显精度差距。v3 要解决的是：**一个模型如何同时处理大、中、小物体？**

### 3.3.2 论文与仓库

| 项目                    | 内容                                                                                                                        |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 论文                    | *YOLOv3: An Incremental Improvement*，arXiv:1804.02767（2018）✅                                                              |
| 发表状态                  | **仅有 arXiv 预印本，从未正式发表于会议** ⚠️——凡标注“CVPR/ECCV 某年 YOLOv3”的说法均有误                                                             |
| 官方实现                  | `pjreddie/darknet`，模型配置 **`cfg/yolov3.cfg`**、**`cfg/yolov3-tiny.cfg`**，权重 **`yolov3.weights`** ✅                          |
| 独立 PyTorch 实现（两个，勿混淆） | **`ultralytics/yolov3`** ✅（Ultralytics 的第一个 YOLO 仓库，现已归档，是 v5 仓库的前身）；**`eriklindernoren/PyTorch-YOLOv3`** ✅（社区高星复现，常用于教学） |

### 3.3.3 核心原理

- **Darknet-53 骨干**：53 层卷积 + 残差连接，替代 Darknet-19，特征提取能力更强。
- **三尺度预测**：在 13×13、26×26、52×52 三层特征图上分别检测大、中、小物体，每层 3 个锚框，共 9 个。
- **类 FPN 融合**：深层特征上采样后与浅层拼接，把语义信息回传给保留空间细节的浅层。
- **分类改为独立 logistic（BCE）**：抛弃 softmax，允许一个框同时属于多个类别（如 person + riding）。

> **图 3-3（待补）**：画出 `13×13 → 上采样 → 拼接 26×26 → 上采样 → 拼接 52×52` 的完整路径，标注每级的感受野与负责的物体尺度。

### 3.3.4 关键公式与损失

每个尺度的损失由三部分组成：定位损失（当时仍用 MSE 类形式）+ 置信度 BCE + 类别 BCE（每一类独立 sigmoid）。

### 3.3.5 消融与关键数字

- COCO：**33.0 AP / 57.9 AP50**，51 ms（Titan X，608 输入）。
- 去掉多尺度融合后，AP_small 明显下降——**证明浅层空间细节不可替代**。

### 3.3.6 争议与批判

- 论文极短、缺少大规模消融，却是架构影响最深远的一代。这本身说明：**架构直觉有时先于严格实验。**
- 三尺度划分是人工先验，融合路径也是手工设计；系统性优化要等到 PANet 与 BiFPN。

### 3.3.7 局限与遗产

- **遗产**：多尺度预测 + 特征融合、独立 logistic 分类、Darknet-53、9 锚框的配置，被 v4 / v5 / v6 / v7 长期沿用。
- **淘汰**：MSE 定位损失、softmax 分类。

## 3.4 YOLOv4（2020）：工程化集大成者

> **命名词条**：Darknet 社区线起点；方法是“消融驱动的系统集成”，而非单点发明。

### 3.4.1 背景与动机

Redmon 于 2020 年宣布退出研究领域，接力棒交到 Alexey Bochkovskiy 手中。v4 的目标是：**在单 GPU 可复现的前提下，用已被验证的技巧组合出速度-精度 Pareto 最优解**。

### 3.4.2 论文与仓库

| 项目                   | 内容                                                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 论文                   | *YOLOv4: Optimal Speed and Accuracy of Object Detection*，arXiv:2004.10934（2020）✅                                     |
| 发表状态                 | 同样**只有 arXiv 预印本，未在任何会议正式发表** ⚠️                                                                                     |
| 官方实现                 | **`AlexeyAB/darknet`**（与 `pjreddie/darknet` 是**两个不同仓库**，不要混用），配置 `cfg/yolov4.cfg`、`cfg/yolov4-csp.cfg` 等 ✅           |
| 独立客户端（两个，均community） | **`WongKinYiu/PyTorch_YOLOv4`** ✅（作者本人（YOLOv7 作者）维护的 PyTorch 版）；**`Tianxiaomo/pytorch-YOLOv4`** ✅（社区高星复现，带完整推理/训练脚本） |

### 3.4.3 核心原理

v4 把技巧分成两类，这个分类本身是它最大的方法论贡献：

- **BoF（Bag of Freebies，只增加训练成本，不增加推理成本）**：Mosaic 数据增强、CutMix、标签平滑、CIoU 损失、CmBN、自对抗训练（SAT）、DropBlock。
- **BoS（Bag of Specials，少量增加推理成本换精度）**：Mish 激活、SPP、SAM、PANet、DIoU-NMS。

结构上：**CSPDarknet53 骨干 → SPP + PANet 颈部 → 锚框检测头**。

> **图 3-4（待补）**：两色网络图，区分“推理期存在”与“仅训练期存在”的模块——这就是 BoF/BoS 的可视化定义。

### 3.4.4 关键公式与损失

**CIoU** 同时惩罚重叠度、中心距与长宽比：

```
L_CIoU = 1 - IoU + ρ²(b, b_gt) / c² + α·v
v = (4/π²) · ( arctan(w_gt/h_gt) - arctan(w/h) )²
α = v / (1 - IoU + v)
```

其中 `ρ` 是中心点距离，`c` 是最小闭包对角线长度。相比 GIoU，它多了长宽比一致性这一项。

**Mosaic**：把 4 张图随机拼接成一张，单张图内同时含 4 倍上下文与更多小目标，也让 BN 的统计量更稳定。

### 3.4.5 消融与关键数字

- COCO：**43.5 AP @ ~65 FPS**（Tesla V100）。
- 论文给出了**逐项累加表**，是 YOLO 系列中最早系统做“Trick 归因”的工作：CSP、Mish、SPP、PANet、Mosaic、CIoU 各贡献若干点。

### 3.4.6 争议与批判

- 方法论价值高于单点创新：它是“系统集成”的范本，但也**继承了归因陷阱**——逐项累加的次序会放大或低估某个组件的贡献（后加的组件在更强的基线上涨点空间更小）。
- 单 GPU 训练是明确的卖点，但 Darknet 生态在此后的维护力度不及 Ultralytics。

### 3.4.7 局限与遗产

- **遗产**：BoF/BoS 术语体系、CSP 结构、PANet 颈部、Mosaic、CIoU，全部成为后续版本的默认配置。
- **遗留**：Darknet 与 PyTorch 两大生态的割裂。

## 3.5 YOLOv5（2020）：PyTorch 时代的开创者

> **命名词条**：Ultralytics 统一平台线起点；它的贡献主要在生态，而非算法。

### 3.5.1 背景与动机

Darknet 在易用性与生态上逐渐落后。Ultralytics 判断，把 YOLO 迁到 PyTorch 生态、并把它做成“开箱即用”的工具，其价值不亚于一次结构创新。

### 3.5.2 论文与仓库

| 项目     | 内容                                                                                                   |
| ------ | ---------------------------------------------------------------------------------------------------- |
| 论文     | **无正式论文** ⚠️。引用时应写明“无同行评审论文，引用官方仓库或文档”，**不要为其编造 arXiv 编号**                                           |
| 专属仓库   | **`ultralytics/yolov5`** ✅ —— 这是 v5 **独有**的仓库（与 v8 之后的 `ultralytics/ultralytics` 不是同一个），当前状态为**已归档** |
| 官方文档   | `https://docs.ultralytics.com/models/yolov5/`                                                        |
| 版本专属标识 | Focus 层、SPPF、自动锚框（AutoAnchor）、`hyp.yaml` 超参文件                                                        |

### 3.5.3 核心原理

结构继承 v4（CSPDarknet53 + PANet + 锚框头），工程上有几处关键改动：

- **Focus 层**（早期版本）：用切片操作替代部分卷积做下采样，后续版本被更高效的普通卷积替代。
- **SPPF**：快速空间金字塔池化，效果接近 SPP 但更快。
- **自适应锚框**：训练前在数据集上自动聚类出最优锚框尺寸。
- **自适应图片缩放**：letterbox 时把填充量降到最小。
- 激活函数改为 **SiLU**。

### 3.5.4 关键配置

损失 = 分类 BCE + 置信度 BCE + CIoU。所有超参集中在 `hyp.yaml`，可随权重一起分发，这是“可复现性”在工程层面的直接体现。

### 3.5.5 消融与关键数字

- v5x：50.7 AP50（COCO，口径见仓库）。
- 显著改善的是训练侧体验：混合精度、梯度累积、显存占用与训练速度。

### 3.5.6 争议与批判

- **“v5 之争”的意义**：它迫使社区正视“没有论文的工程实现能否称为一个版本”。实践给出的答案是——**看它是否改变了社区实践**，而 v5 显然做到了。
- **可复现性最强**：一键训练、验证、导出的工具链，使它成为后来几乎所有工作的默认基线。这既是贡献，也是“基线惰性”的来源：社区很少再探索默认配置之外的超参空间。

### 3.5.7 局限与遗产

- **遗产**：Ultralytics 工具链范式（CLI + Python API + 导出矩阵）、自动锚框、letterbox、`hyp.yaml`、SPPF。
- **淘汰**：Focus 层、锚框（v8 起）。
- **注意**：许可协议（GPL/AGPL 系）对商业使用有实质影响，落地前必须确认。

## 3.6 YOLOv6（2022）：工业部署导向

> **命名词条**：美团独立分支（v6.0 → v6.1 → v6.2 → v6.3）；目标函数是吞吐与硬件适配，而非纯精度。

### 3.6.1 背景与动机

美团视觉团队需要一套面向大规模工业部署的检测框架。它的问题意识是：**把部署约束前置为架构设计目标**，而不是事后压缩。

### 3.6.2 论文与仓库

| 项目   | 内容                                                                                                      |
| ---- | ------------------------------------------------------------------------------------------------------- |
| 论文   | *YOLOv6: A Single-Stage Object Detection Framework for Industrial Applications*，arXiv:2209.02976（2022）✅ |
| 专属仓库 | **`meituan/YOLOv6`** ✅（美团官方，与其它任何 YOLO 仓库无代码关系）                                                         |
| 文档入口 | 仓库内 `docs/` 目录，另有 `configs/` 下分型号配置                                                                     |
| 注意   | v6.0 → v6.1 → v6.2 → v6.3 迭代幅度大，**引用数字时必须写明具体子版本** ⚠️                                                   |

### 3.6.3 核心原理

- **EfficientRep 骨干 / Rep-PAN 颈部**：采用 RepVGG 式“训练多分支、推理融合单路”。
- **解耦检测头**：分类与回归分支分离，降低任务冲突。
- **Anchor-free**（v6.1 起）+ **TAL（Task Alignment Learning）** 标签分配 + **SIoU** 损失。
- **量化友好**：原生支持 PTQ / QAT，为 INT8 部署设计。

### 3.6.4 关键公式与机制

**重参数化恒等**：训练时的三分支结构

```
Conv3×3  +  Conv1×1  +  Identity   ──融合──▶   单个 Conv3×3
```

推理时把三条支路的权重等价地折叠成一个卷积核，**以零额外推理开销换取多分支带来的训练收益**。

**TAL 对齐度量**：`t = s^α · u^β`，`s` 为分类得分、`u` 为预测框与真实框的 IoU，用两者的联合度量挑选正样本。

### 3.6.5 消融与关键数字

- v6-s：约 43.1 AP / 52.5 AP50（口径见论文）；T4 上 TensorRT-FP16 延迟在亚毫秒到毫秒级。
- 消融覆盖 TAL、解耦头、SIoU 的逐项贡献。

### 3.6.6 争议与批判

- **重参数化的代价常被低估**：融合后的结构虽快，但**约束了架构搜索空间**（训练期不能用任意分支），且对量化并不总是友好，需要专门处理。
- **目标函数不同**：论文优先报告 T4 与量化后的指标，而不是纯 COCO 精度。这是取舍差异，不是能力差异。

### 3.6.7 局限与遗产

- **遗产**：Rep 结构、TAL（被 v8 采用后成为主流）、SIoU、完整的 QAT 流程。
- **遗留**：生态独立于 Ultralytics，文档与预训练权重的可达性较弱。

```bash
python tools/infer.py --weights yolov6s.pt --source data/images/
```

## 3.7 YOLOv7（2022）：Bag-of-Freebies 的极致

> **命名词条**：Darknet 社区线（v4 团队）；把“训练期技巧零推理成本”这条思路推到极致。

### 3.7.1 背景与动机

v4 团队希望在不增加推理成本的前提下继续提升精度，并让架构缩放更系统化。

### 3.7.2 论文与仓库

| 项目     | 内容                                                                                                                        |
| ------ | ------------------------------------------------------------------------------------------------------------------------- |
| 论文     | *YOLOv7: Trainable bag-of-freebies sets new state-of-the-art for real-time object detectors*，CVPR 2023，arXiv:2207.02696 ✅ |
| 专属仓库   | **`WongKinYiu/yolov7`** ✅（与作者团队的 `yolov9` 是不同的仓库）                                                                         |
| 版本专属标识 | E-ELAN、计划重参数化（RepConv）、辅助头 + 主头（lead/aux head）                                                                            |

### 3.7.3 核心原理

- **E-ELAN**：扩展的高效层聚合网络，通过分组卷积与通道重排控制**最短与最长梯度路径**，在不破坏原始梯度路径的前提下增强学习能力。
- **复合缩放**：为 tiny 到 large 的整个家族设计一致的深度 / 宽度 / 通道缩放方案。
- **可训练的 BoF**：
  - **计划重参数化卷积**：训练期使用带恒等分支的 RepConv，推理前替换为去分支的版本，以匹配 ELAN 的梯度路径。
  - **辅助头训练 + 主头推理**：辅助头只在训练期提供梯度。
  - **coarse-to-fine 标签分配**：辅助头做粗分配，主头做细分配。

### 3.7.4 关键机制

```
训练期：  lead head  +  aux head（多层）      ← 都产生梯度
推理期：  仅保留 lead head                    ← 辅助结构整段丢弃
```

### 3.7.5 消融与关键数字

- v7-E6：**56.8 AP**（COCO，口径见论文）；论文宣称在 5–160 FPS 全区间优于同期检测器。

### 3.7.6 争议与批判

- **“零推理成本”的边界**：辅助头确实不进入推理，但**显著增加训练显存与时间**。BoF 的本质是把成本从推理期搬到训练期，而不是消除成本。
- **可迁移性存疑**：E-ELAN 的分组与重排设计在非 YOLO 架构上是否同样有效，缺少系统验证。

### 3.7.7 局限与遗产

- **遗产**：辅助头训练、计划重参数化、coarse-to-fine 分配、复合缩放。
- **遗留**：训练复杂度高，超参较为脆弱。

## 3.8 YOLOv8（2023）：统一多任务平台

> **命名词条**：Ultralytics 统一平台线的核心节点；它与同期的 v9、v10 是并列关系，而非继承关系。

### 3.8.1 背景与动机

v5 的架构逐渐老化，同时社区已经不满足于“只能做检测”。v8 要回答两个问题：**标签分配是否比骨干结构更能决定性能？如何用一套接口覆盖多任务？**

### 3.8.2 论文与仓库

| 项目     | 内容                                                                                  |
| ------ | ----------------------------------------------------------------------------------- |
| 论文     | **无独立论文** ⚠️。技术细节以官方文档与 Ultralytics 系列综述为准，引用时不要虚构论文                                |
| 统一仓库   | `ultralytics/ultralytics` ✅                                                         |
| 模型专属入口 | `https://docs.ultralytics.com/models/yolov8/` ✅（**区分同一仓库不同版本，看文档路径与模型权重名，而不是仓库地址**） |
| 版本专属标识 | C2f、Anchor-free 解耦头、TAL + DFL、`.pt` 权重名形如 `yolov8n.pt`                              |

> **关于「四个版本共用同一个仓库」**：自 v8 起，Ultralytics 把所有模型**合并进单一 Python 包 `ultralytics`**（即 `ultralytics/ultralytics`），v8、v11、v26、v27 都出自这一个仓库。因此区分版本要看**权重名与文档路径**：`yolov8n.pt` / `yolo11n.pt` / `yolo26n.pt` / `yolo27n.pt`。这是 Ultralytics 的产品策略，不是引用错误。

### 3.8.3 核心原理

- **C2f 模块**（替代 C3）：提供更丰富的跨层梯度流。
- **Anchor-free 解耦头**：直接预测中心与尺寸，不再依赖先验框。
- **TAL（Task-Aligned Assigner）**：按 `t = s^α·u^β` 动态分配正样本。
- **DFL（分布焦点损失）**：把框坐标建模为离散分布，用期望作为回归值。
- **去掉 objectness**：不再单独预测“有无物体”，分类头使用 BCE / VFL。
- **统一 API**：`YOLO()` 对象通过不同任务参数支持检测、分割、分类、姿态、旋转框。

> **图 3-5（待补）**：同一个真实框在 TAL 下如何动态选中不同数量的正样本，并标注 `α, β` 变化对分配结果的影响。

### 3.8.4 关键公式与损失

- **DFL**：把连续坐标 `y` 化为相邻两个 bin 的交叉熵

```
L_DFL = - Σ [ (y_{i+1} - y)·log(S_i) + (y - y_i)·log(S_{i+1}) ]
```

- **总损失**：`L = λ_box·L_CIoU + λ_dfl·L_DFL + λ_cls·L_BCE/VFL`
- **TAL**：`t = s^α · u^β`

### 3.8.5 消融与关键数字

- v8x：53.9 AP（COCO val2017，口径见官方）；提供 n / s / m / l / x 五档。
- 消融显示 DFL 与 TAL 各自贡献明显：去掉任一都会掉点。

### 3.8.6 争议与批判

- **DFL 的代价被低估**：它提升精度，却**破坏导出友好性**——分布积分在 ONNX / TensorRT 上需要额外算子支撑。这正是 v26 移除 DFL 的直接动因。
- **TAL 是分配范式的转向点**：此后“分配比结构更重要”逐渐成为共识。把 v8 与 v5 的骨干结构作对比会发现，两者差异其实很小，性能提升主要来自分配与损失。
- **验证集调参风险**：默认超参在 COCO 上高度调优，迁移到自定义数据时应重新搜索学习率与增强强度。

### 3.8.7 局限与遗产

- **遗产**：C2f、Anchor-free 解耦头、TAL、DFL、统一 `YOLO()` API 与多任务矩阵。
- **遗留**：DFL 导出复杂、无锚头在小目标上的召回代价。

```python
results = model("https://ultralytics.com/images/bus.jpg")
```

## 3.9 YOLOv9（2024）：解决信息瓶颈

> **命名词条**：Darknet 社区线（v7 团队）；用信息论语言重新表述“深层网络会丢失信息”。

### 3.9.1 背景与动机

网络越深，浅层信息在前向与反向传播中损耗越多，小物体与复杂场景最先受害。v9 试图回答：**能否用量化的信息论视角刻画这种损耗，并显式补偿它？**

### 3.9.2 论文与仓库

| 项目     | 内容                                                                                                                  |
| ------ | ------------------------------------------------------------------------------------------------------------------- |
| 论文     | *YOLOv9: Learning What You Want to Learn Using Programmable Gradient Information*，arXiv:2402.13616 ✅（收录于 ECCV 2024） |
| 专属仓库   | **`WongKinYiu/yolov9`** ✅（与同作者的 `yolov7` 是两个仓库）                                                                     |
| 版本专属标识 | PGI（可编程梯度信息）、GELAN、辅助可逆分支                                                                                           |

### 3.9.3 核心原理

- **PGI（可编程梯度信息）**：由主分支 + 辅助可逆分支 + 多级辅助信息组成，核心是**让深层网络在训练时仍能获得未损耗的输入信息**。
- **GELAN**：融合 CSPNet 与 ELAN 的优点，兼顾轻量与特征聚合能力。
- **可逆架构**：辅助分支设计为可逆，使反向传播时的信息损失最小。

> **图 3-6（待补）**：用“水管漏水”作类比——源头 → 中段补水（辅助分支）→ 末端水压（判别性能），并标明辅助结构**只在训练期存在、推理期移除**。

### 3.9.4 关键概念

信息瓶颈的论证思路：前向传递必然损失信息，可用 `I(X,Y) ≥ I(X, f_θ(X))` 一类的不等式描述；PGI 通过辅助分支在训练期补偿这部分损失。推理时只保留主分支，因此**本质仍是一次 BoF**。

### 3.9.5 消融与关键数字

- v9e：55.6 AP（COCO，口径见论文）；论文给出 GELAN 与 PGI 的逐项消融。

### 3.9.6 争议与批判

- **叙事溢价**：PGI 的辅助分支与 v7 的 aux head 在工程上高度相似，但其**理论包装（信息瓶颈）比机制本身更引人注目**。阅读时需要把“叙事”和“证据”分开看。
- 可复现性较好：仓库提供多尺寸权重。

### 3.9.7 局限与遗产

- **遗产**：GELAN 这一轻量聚合结构；用信息论解释检测的话语体系。
- **遗留**：辅助分支带来的训练开销；理论论证与工程收益之间的量化对应仍不清晰。

```bash
pip install -r requirements.txt
python detect.py --weights yolov9-c.pt --source data/images/horses.jpg
```

## 3.10 YOLOv10（2024）：告别 NMS

> **命名词条**：清华 THU-MIG 独立分支；罕见的范式级节点——把 NMS 从推理链路中移除。

### 3.10.1 背景与动机

NMS 不可导、延迟随候选数波动、依赖 IoU 阈值超参。v10 的问题是：**能否训练出天然无重叠、可端到端推理的检测器？**

### 3.10.2 论文与仓库

| 项目     | 内容                                                                                    |
| ------ | ------------------------------------------------------------------------------------- |
| 论文     | *YOLOv10: Real-Time End-to-End Object Detection*，arXiv:2405.14458 ✅（收录于 NeurIPS 2024） |
| 专属仓库   | **`THU-MIG/yolov10`** ✅（清华大学 THU-MIG 实验室，与 Ultralytics / 美团 / WongKinYiu 均无关）         |
| 版本专属标识 | 一致双分配、NMS-free、部分自注意力 PSA                                                             |
| 衍生项目   | 同一实验室的 YOLOE 见 `THU-MIG/yoloe` ⚠️                                                     |

### 3.10.3 核心原理

- **一致双分配**：训练时**同时**使用一对多分支（一个真实框对应多个正样本，监督信号丰富）和一对一分支（一个真实框只对应一个正样本），两者损失加权联合；推理时**只保留一对一分支**，因此不需要 NMS。
- **一致匹配度量**：两个分支使用同一套匹配度量，保证监督一致。
- **效率优化**：rank-guided 模块设计、大核卷积、部分自注意力（PSA）、空间-通道解耦下采样。

> **图 3-7（待补）**：画出“训练双头 → 推理单头”的切换，标注一对多与一对一各自的输出框数量，并展示推理输出天然无重叠。

### 3.10.4 关键公式与损失

- 双分配总损失：`L = L_one2many + λ·L_one2one`
- 一对一分支采用最优匹配思想，与 DETR 一脉相承；匹配度量沿用 `s^α·u^β` 家族。

### 3.10.5 消融与关键数字

- v10x：54.4 AP（COCO），端到端延迟优于同档 v8 / v9（论文给出 T4 延迟表）。
- 关键观察：去掉 NMS 后，**端到端延迟的方差显著下降**（P99 更稳定）。

### 3.10.6 争议与批判

- **贡献是范式级的**：把“无 NMS”从高算力的 DETR 系下放到实时检测器，且精度不降——这是最硬的证据。
- **代价**：一对一分支依赖更长的训练与更精细的匹配，**训练稳定性对小数据集不友好**。
- **与 DETR 的关系**：本质上是“用一对多监督去辅助一对一学习”，回答的正是 DETR 收敛慢的经典批评。

### 3.10.7 局限与遗产

- **遗产**：NMS-free 成为 v26 的默认前提；“双分配 + 一致度量”被广泛借鉴。
- **遗留**：一对一匹配在小数据与长尾类别上的表现、训练成本。

### 3.10.8 Demo 与落地

```bash

cd yolov10
pip install -r requirements.txt
python app.py     # 启动 Gradio 演示界面
```

部署提示：导出 ONNX 后应确认**输出无需 NMS**，这是端到端带来的核心收益。

## 3.11 YOLO11（2024）：注意力增强

### 3.11.1 背景与动机

C2f 与检测头仍有提升空间，尤其是遮挡与复杂场景。问题是：**轻量注意力能否在不牺牲延迟的前提下改善这些场景？**

- **C2PSA**：在 SPPF 之后引入**部分自注意力**（Partial Self-Attention），增强全局建模。

- **“部分化”是折中，不是新范式**：全注意力延迟高，C2PSA 只对部分通道做注意力。这是精度-延迟折中的工程解，理论新颖性有限。

## 3.12 YOLOv12（2025）：注意力中心架构

> **命名词条**：独立学术分支；把注意力从“插件”升级为“架构主体”。

### 3.12.1 背景与动机

卷积在全局建模上弱于 Transformer，而直接堆 Transformer 又会拖慢速度。v12 的问题是：**能否在实时约束下让注意力成为架构主体，而非附加组件？**

### 3.12.2 论文与仓库

| 项目     | 内容                                                                                                    |
| ------ | ----------------------------------------------------------------------------------------------------- |
| 论文     | *YOLOv12: Attention-Centric Real-Time Object Detectors*，arXiv:2502.12524 ⚠️（**会议收录状态未证实**；论文以预印本形式公开） |
| 专属仓库   | **`sunsmarterjie/yolov12`** ✅（个人仓库，与 Ultralytics 无关）                                                  |
| 版本专属标识 | A² 区域注意力、R-ELAN                                                                                       |
| 提醒     | 凡称 v12 被 NeurIPS / ICLR 收录的说法，引用前必须回到会议官网核对 ⚠️                                                        |

### 3.12.3 核心原理

- **A²（Area Attention）**：把特征图划分成若干区域，**区域内做注意力、区域间用轻量机制聚合**，在保持大感受野的同时把复杂度从 `O(N²)` 降到近似线性。
- **R-ELAN（残差高效层聚合网络）**：把残差连接与 ELAN 结合，优化梯度流动。
- **注意力中心设计**：把注意力模块融入骨干与颈部，并配合 FlashAttention 等高效内核。

> **图 3-8（待补）**：把一张 80×80 特征图切成 k 个区域，画出“区域内全连接注意力 + 区域间聚合”的两级结构，标注复杂度分解与延迟实测。

### 3.12.4 关键公式

论文给出了区域注意力的复杂度分解式（正文引用时须给出原式）。核心思想是：把全局注意力的平方复杂度拆成“区域内 + 区域间”两部分，代价大幅下降。

### 3.12.5 消融与关键数字

- 论文宣称在同等精度下**比 v10 / v11 快约 40%**（口径待核）。
- 收益对硬件敏感：在支持高效注意力内核的 GPU 上更明显。

### 3.12.6 争议与批判

- **“区域”是一种稀疏注意力的归纳偏置**，与窗口注意力、局部注意力同源；其创新更多体现在工程组合与在 YOLO 语境下的验证。
- **硬件依赖强**：GPU 上收益明显，纯 CPU 边缘设备上的优势可能被削弱。
- 需要并列参考**第三方复现结果**，而非仅作者自评。

### 3.12.7 局限与遗产

- **遗产**：证明了区域注意力可用于实时检测；推动“注意力中心”这一叙事。
- **遗留**：CPU 与低端 NPU 上的收益边界、训练稳定性。

# 4. 横向专题：把十年拉成一条线看

第 3 节按版本纵向展开，这一节换一个方向——把十年拆成**十二条横向主线**，逐个拉直。这样做的理由很实际：很多创新在单个版本里看不出分量，只有放进同一条主线，才能判断它是真突破还是换汤不换药。每条主线统一按“演进路线 → 关键权衡 → 具体数字与公式 → 图 → 开放问题”展开。

## 4.1 骨干网络演进

**演进路线**：

| 骨干             | 首现       | 核心结构                        | 相对参照的关键事实                                               |
| -------------- | -------- | --------------------------- | ------------------------------------------------------- |
| Darknet-19     | v2       | 19 层卷积 + 5 次池化              | 精度接近 VGG16，计算量显著更小                                      |
| Darknet-53     | v3       | 53 层卷积 + 残差                 | top-1 77.2% / top-5 93.8%，精度与 ResNet-152 相当，但速度快约 1.5 倍 |
| CSPDarknet53   | v4 / v5  | 引入跨阶段部分连接（CSP）              | 把梯度流分成两路，减少重复计算、增强梯度传播                                  |
| EfficientRep   | v6       | RepVGG 式三分支（训练）→ 单路（推理）     | 训练期多分支、推理期融合，几乎零推理开销                                    |
| E-ELAN / GELAN | v7 / v9  | 分组卷积 + 通道重排 / CSP + ELAN 融合 | 控制最短与最长梯度路径，增强学习能力而不破坏原路径                               |
| C2f / C3k2     | v8 / v11 | 跨阶段特征复用，卷积核可配置              | 更丰富的跨层梯度流，参数量更可控                                        |
| 区域注意力          | v12      | 区域内注意力 + 区域间聚合              | 把全局注意力的平方复杂度拆成两级                                        |

**三个真正的设计杠杆**（其余都是细节）：

1. **连接方式**：残差（v3）→ 跨阶段（v4）→ 特征复用（v8）。它决定梯度能传多深。
2. **训练 / 推理结构解耦**：重参数化（v6）与辅助分支（v7、v9）。**训练期可以复杂，推理期必须简单**——这是过去六年最重要的工程共识。
3. **算子类型**：卷积 ↔ 注意力（v11、v12）。它决定感受野与硬件友好度的组合。

## 4.2 颈部与多尺度融合

**每一级的分工**：

```
输入图像
  │
  ├─ stride 8  → P3 特征图（分辨率最高）→ 负责小物体
  ├─ stride 16 → P4 特征图              → 负责中物体
  └─ stride 32 → P5 特征图（语义最强）  → 负责大物体

融合方向：
  自顶向下（P5 → P4 → P3）：把语义传给浅层，解决“浅层不知道是什么”
  自底向上（P3 → P4 → P5）：把定位细节传给深层，解决“深层不知道在哪里”
```

- **FPN**（v3 借鉴）：只做自顶向下。
- **PANet**（v4 / v5）：补上自底向上，形成双向路径。
- **Rep-PAN**（v6）：把双向路径的融合单元重参数化。
- **C2f 融合**（v8）与**注意力融合**（v11 / v12）：换融合算子，不换拓扑。

**关键权衡：到底要不要 P2（stride 4）？** 小物体最受益，但特征图面积是 P3 的 4 倍，计算与显存同步放大 4 倍。多数通用模型止步于 P3；只有在密集小目标场景（遥感、质检、无人机）才值得引入 P2 并配合裁剪训练。

> **图 4-2（待补）**：画出 P3 / P4 / P5 三层与双向融合的完整拓扑，每条边标注方向、融合算子（拼接 / 相加 / 加权）与对应 stride。再叠一张典型图像的物体尺寸分布直方图，说明“为什么设定三个尺度而不是两个或四个”。

**开放问题**：融合路径的拓扑能否可搜索？把尺度分配当作超参自动优化，是否比人工设三档更划算？

## 4.3 检测头：耦合 → 解耦 → 无锚 → 端到端

| 代际   | 代表版本      | 每个位置输出什么                      | 是否需要锚框  | 是否需 NMS |
| ---- | --------- | ----------------------------- | ------- | ------- |
| 耦合头  | v1–v5     | 单分支输出 `5 + C`（或 `A×(5+C)`）    | v2 起需要  | 需要      |
| 解耦头  | v6 / v8   | 分类分支 `C` 与回归分支 `4`（或 `4×l`）分离 | v6 起可无锚 | 需要      |
| 无锚头  | v6.1 / v8 | 直接预测中心与尺寸                     | 不需要     | 需要      |
| 双分配头 | v10       | 一对多 + 一对一两个头，推理只用一对一          | 不需要     | **不需要** |

**为什么解耦有效？** 分类关心“是什么”，回归关心“在哪里”，两者的最优特征变换并不一致；共享一层卷积会互相干扰。工业上常见的量化结论是：解耦头带来约 1 mAP 级别的提升，代价是极小的额外延迟——这是一笔非常划算的交易。

**锚框的退出**：锚框的本质是把“回归任意尺寸”简化为“回归相对先验的偏移”，代价是引入超参（数量、尺寸、比例）与正样本匹配的复杂度。当标签分配足够聪明（见 4.4）时，锚框就不再必要。

**开放问题**：所有尺度都解耦是否必要？在小目标分支上，一对一分配的召回损失用什么补？

## 4.4 标签分配演进（十年里最被低估的变量）

| 代际    | 代表             | 正样本如何定义                     | 是否有硬阈值         |
| ----- | -------------- | --------------------------- | -------------- |
| 静态分配  | v2–v5          | IoU 超过阈值，或与锚框最优匹配           | 有（如 IoU > 0.5） |
| 动态分配  | v6 中期（SimOTA）  | 按代价排序后动态取 top-k             | k 由代价和决定       |
| 对齐分配  | v6.1 / v8（TAL） | 按 `t = s^α · u^β` 排序取 top-k | 相对             |
| 一致双分配 | v10            | 一对多 + 一对一，两套分配同时监督          | 无（一对一为最优匹配）    |

**核心公式**：`t = s^α · u^β`，`s` 为分类得分、`u` 为预测框与真实框的 IoU。它把“分类准”和“框得准”合成一个排序依据，因此正样本天然是两者都好的预测。

**为什么说它比结构更重要？** 一个可验证的观察是：v5 与 v8 的骨干结构差异很小，但性能差距明显，而差距的主要来源是分配与损失。做一次干净的控制变量实验（把 v8 的分配装到 v5 的结构上）就能看出这一点——这类实验目前仍很稀缺。

> **图 4-4（待补）**：固定同一个真实框与 9 个候选预测，逐步展示四代分配各自选中哪些正样本：静态阈值可能只选 1 个（阈值设得不好时甚至 0 个），动态 top-k 选 3 个，TAL 按对齐度选质量最高的 3 个，一对一强制只选 1 个。这张图能直接解释“为什么分配变化会带来精度变化”。

**开放问题**：分配策略与数据规模的关系是什么？小数据集下动态分配是否仍优于静态？长尾类别是否应获得更多正样本？

## 4.5 损失函数演进（IoU 家族与 DFL）

| 损失                | 首现   | 解决的问题      | 新增的惩罚项         |
| ----------------- | ---- | ---------- | -------------- |
| MSE（对 x, y, w, h） | v1   | 无          | 无（与 IoU 不直接相关） |
| IoU               | 概念沿用 | 与评测指标对齐    | 重叠度            |
| GIoU              | v4   | 无重叠时梯度消失   | 最小闭包面积         |
| DIoU              | v4   | 中心点远离时收敛慢  | 中心距            |
| CIoU              | v4   | 长宽比失配      | 长宽比            |
| EIoU              | 主线之外 | 长宽比被耦合在一起  | 宽、高各自独立惩罚      |
| SIoU              | v6   | 忽略方向（角度）代价 | 角度 + 距离 + 形状   |
| DFL               | v8   | 边界模糊、标注噪声  | 把坐标建模为离散分布     |

**关键公式**（同一对“错位框”下逐项对比）：

```
GIoU = IoU - |C \ (A ∪ B)| / |C|              C 为最小闭包
DIoU = IoU - ρ²(b, b_gt) / c²                  ρ 为中心距，c 为闭包对角线
CIoU = DIoU - α·v,  v = (4/π²)(arctan(w_gt/h_gt) - arctan(w/h))²
DFL  = -Σ [ (y_{i+1} - y)·log(S_i) + (y - y_i)·log(S_{i+1}) ]   相邻两 bin 的交叉熵
```

**分类损失**：Softmax CE（v1–v3）→ BCE 多标签（v3 起）→ Focal / VFL（v8 起）。BCE 的引入是为了让一个框能同时属于多个类别；VFL 用预测框与真实框的 IoU 作为目标权重，让“框得准的预测”承担更大的分类权重。

> **图 4-5（待补）**：同一对错位框，分别计算 IoU / GIoU / DIoU / CIoU 的数值，用柱状图展示每一代新增惩罚项带来的边际变化。要能看出：当两框完全不相交时，只有 IoU 会失效。

**开放问题**：IoU 家族的“可组合性”是否已经饱和？DFL 的收益能否用导出友好的方式（例如直接回归 + 分布正则）保留下来？

**开放问题**：在低于 1 GFLOPs 的区间，注意力是否仍然值得？线性注意力能否替代区域注意力？

## 4.8 模型缩放与重参数化

**缩放**：v7 提出复合缩放，把深度系数、宽度系数与输入分辨率联动调整；v8 / v11 用预置的 n / s / m / l / x 五档替代搜索。

**重参数化的数学骨架**（推理时零成本的关键）：

```
训练期：  y = BN₃ₓ₃(Conv₃ₓ₃(x)) + BN₁ₓ₁(Conv₁ₓ₁(x)) + BN_id(x)
推理期：  y = Conv₃ₓ₃_fused(x)
```

融合的合法性来自两点：① BN 在推理期是线性变换，可折叠进卷积权重；② `Conv1×1` 与 `Identity` 都可以用 `3×3` 核（补零）等价表示，因此三路可以逐元素相加合并为一个卷积核。

> **图 4-8（待补）**：给出一个具体数值例子（例如输入通道 1、输出通道 1），把三分支的权重与 BN 参数逐步折叠成单卷积核，最后验证两者对同一输入输出完全一致。

**开放问题**：重参数化对量化与稀疏化的友好度如何量化？缩放规则能否自动搜索而非人工设档？

## 4.9 知识蒸馏、伪标签与自训练

- **路线**：v6 的通道级蒸馏 → 用大模型监督小模型 → 无标注数据上的伪标签迭代 → 自监督预训练。
- **通道蒸馏的具体做法**（v6）：让学生网络的 1×1 卷积去拟合教师网络某一层的特征通道响应，相当于把“特征语言”对齐，而不是只对齐最终输出。
- **伪标签的关键风险**：确认偏差——模型把错误预测当作真值，越训越自信。缓解手段包括置信度阈值、类别均衡采样、教师-学生双模型互检。

**开放问题**：能否用可验证的伪标签筛选（例如多模型一致性 + 几何一致性）替代单纯的置信度阈值？

## 4.10 量化、剪枝与推理加速

| 环节  | 选项                                           | 适用场景                               | 典型代价               |
| --- | -------------------------------------------- | ---------------------------------- | ------------------ |
| 量化  | PTQ（训练后量化）                                   | 有现成权重、快速验证                         | INT8 下常见掉 0.5–2 AP |
| 量化  | QAT（量化感知训练）                                  | 精度敏感、可重训                           | 需完整训练流程与校准         |
| 剪枝  | 结构化（通道）                                      | 通用加速，硬件友好                          | 检测头对剪枝敏感，需谨慎       |
| 剪枝  | 非结构化（权重）                                     | 压缩存储                               | 通用硬件收益有限           |
| 引擎  | TensorRT / OpenVINO / NCNN / TFLite / CoreML | NVIDIA / Intel / ARM / 移动端 / Apple | 算子支持度各异            |

**部署链路上最容易出错的三件事**：

1. **letterbox 必须在图内**。若把缩放填充分配给宿主代码，边缘端常常实现不一致，导致精度与云端不符。
2. **NMS 位置要明确**。传统模型把 NMS 留在宿主机上，v10 / v26 之后可以彻底移出。
3. **动态 shape 要提前确认**。边缘设备对动态输入尺寸的支持千差万别，固定尺寸往往是最稳的选择。

**开放问题**：端到端 QAT 与“移除 DFL / NMS”之间的协同收益有多大？移除算子后再做量化感知训练，是否能让掉点进一步缩小？

## 4.11 开放词汇与多模态

- **路线**：WordTree（v2 的层次化类别）→ CLIP 式文本编码 → YOLO-World → YOLOE-27（文本 / 视觉 / 无提示三种模式）。
- **关键技术是“重参数化词汇”**：把文本编码器产出的类别嵌入，在推理前离线融合进检测头的分类卷积权重。这样推理时模型看到的仍是普通卷积，**开放词汇的额外成本被前置到了离线阶段**。
- **评测上的坑**：LVIS 的评测协议把类别分为 base（训练中见过）与 novel（未见），常用指标是 AP_r（稀有类）。这与 COCO 的 AP 不可直接比较；只看 base 类别的分数容易“刷分”。

**开放问题**：novel 类别的泛化上限在哪里，是否受限于文本编码器？领域漂移下如何低成本更新词表？

## 4.12 多任务统一

| 任务      | 输出头          | 损失               | 备注           |
| ------- | ------------ | ---------------- | ------------ |
| 检测      | 框 + 类别       | CIoU / DFL + BCE | 主线任务         |
| 实例分割    | 检测头 + 掩码原型系数 | 掩码 BCE           | 复用检测框，增加原型分支 |
| 语义分割    | 逐像素分类        | 逐像素交叉熵           | 通常不依赖检测头     |
| 姿态估计    | 关键点热图或坐标回归   | 热图 MSE / 坐标 L1   | 分辨率敏感        |
| 旋转框 OBB | 框 + 角度       | 角度周期化损失 + CIoU   | 角度需处理周期性     |
| 分类      | 全局类别         | 交叉熵              | 复用骨干，去检测头    |
| 深度估计    | 逐像素回归        | 尺度不变损失           | 需要深度标注       |

**多任务的真实难点是梯度冲突**：不同任务的损失量级与收敛速度不同，共享骨干时容易互相干扰。常见做法是调 loss 权重、梯度归一化、或在浅层共享深层分家。

**开放问题**：多任务统一带来的是正迁移，还是仅仅是工程上的复用？在任务相关度高（检测 + 实例分割）与相关度低（检测 + 深度）时，结论是否不同？

# 5. 前沿与开放问题

## 5.1 值得做的十个问题

1. **分配 vs 结构**：把 v8 的结构装回 v5 的分配（或反之），性能差多少？干净的控制变量实验仍然稀缺。
2. **端到端极限**：无 NMS 之后，下一个可以移除的环节是什么？（DFL 已被移除，接下来是后处理归一化？）
3. **小目标瓶颈**：AP_small 的十年曲线为何远慢于 AP_large？
4. **边缘 Pareto**：CPU / NPU 上的最优结构与 GPU 上的最优结构，是否本质不同？
5. **注意力的性价比**：在低于 1 GFLOPs 的区间，注意力是否仍然值得？
6. **开放词汇的可信评测**：如何避免在 base 类别上“刷分”？
7. **标签高效**：半监督与自监督能否把标注需求降低一个数量级？
8. **可复现性危机**：COCO 上 ±1 AP 的复现差异，是否已经超出多数论文的增益？
9. **长尾与分布外**：YOLO 在 OOD 场景下的失败模式如何系统刻画？
10. **统一评测协议**：呼吁一个同时涵盖 COCO / LVIS、边缘延迟与功耗的跨版本基准。

## 5.2 方法论反思

- **叙事溢价**：好的理论包装（如“信息瓶颈”）会放大机制的实际贡献，读者需要把叙事与证据分开。
- **基线惰性**：社区过度依赖 Ultralytics 的默认配置，导致基线本身被固化，抑制了其它超参空间的探索。
- **工程即贡献**：v5 / v8 的无论文路径证明，改变社区实践是一种被低估的贡献形式。
- **负结果的价值**：BoF 类工作应同时报告“不涨点的 Trick”——目前几乎无人这么做。
